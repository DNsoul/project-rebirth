# Форматы и ключи

Этот документ описывает то, что лежит в gist и чем это подписано. Его реализуют
дважды: на Go (сервер и утилита для ПК) и на Dart (приложения). Обе реализации
обязаны проходить одни и те же контрольные векторы из `vectors.json`.

## 1. Ключи

| Ключ | Тип | Где лежит закрытая часть | Зачем |
|---|---|---|---|
| Главный (`root`) | Ed25519 | Keystore телефона | Заверяет ключ серверов, подписывает команды и отзыв |
| Запасной (`backup`) | Ed25519 | Офлайн: зашифрованный файл или QR | То же самое, если телефон потерян |
| Ключ серверов | Ed25519 | На сервере, передаётся преемнику | Подписывает конфиг и статус |
| Ключ содержимого | 32 байта | Зашит во все сборки приложений | Шифрует всё, что попадает в gist |

Главный и запасной равноправны. Открытые части обоих и ключ содержимого зашиты
в сборки приложений.

Ключ содержимого есть у всех, у кого есть приложение. Это и задумано: наличие
приложения даёт доступ. Защиту от подмены сервера даёт не шифрование, а подпись:
подделать её без главного или запасного ключа нельзя.

## 2. Конверт

Всё, что кладётся в gist, — это одна строка:

```
base64url( nonce[12] || AES-256-GCM(ключ содержимого, nonce, открытый текст) )
```

Base64url без выравнивающих символов `=`. Заголовка-метки нет намеренно: строка
не несёт никакого узнаваемого признака. Если расшифровка не удалась, значит ключ
не тот или это посторонние данные.

Открытый текст — это JSON одного из документов ниже.

## 3. Что именно подписывается

Подписывается не JSON, а явно собранная строка байтов. Так две независимые
реализации всегда получают одно и то же, и не нужен канонический вид JSON.

Правила сборки:

- строка начинается с имени документа и нулевого байта, например
  `awg-rotator/cert/v1\0`;
- целые пишутся как big-endian: `u32` — 4 байта, `i64` — 8 байт;
- переменные поля пишутся как `u32(длина) || сами байты` (дальше `lp(x)`);
- строки сначала переводятся в UTF-8, потом пишутся как `lp`.

Поле `sig` в подписываемую строку не входит.

## 4. Документы

Во всех документах двоичные значения записаны в base64url, время — в секундах
Unix.

### 4.1. Сертификат (`cert`)

Заявляет, что ключ серверов можно доверять. Подписан главным или запасным ключом.

```json
{ "epoch": 3, "nbf": 1762400000, "exp": 1767584000,
  "pub": "<ключ серверов>", "by": "root", "sig": "<подпись>" }
```

Подписываемая строка:

```
"awg-rotator/cert/v1\0" || u32(epoch) || i64(nbf) || i64(exp) || lp(pub) || lp(by)
```

`epoch` — номер поколения ключа серверов. Растёт при каждой выдаче нового.

### 4.2. Конфиг и статус (`doc`)

Один формат на двоих, различаются полем `kind`: `config` — настройки
подключения, `status` — отчёт сервера о себе.

```json
{ "v": 1, "kind": "config", "seq": 12,
  "iat": 1762400000, "exp": 1767584000,
  "cert": { ... }, "body": "<текст>", "sig": "<подпись>" }
```

Подписываемая строка:

```
"awg-rotator/doc/v1\0" || lp(kind) || u64(seq) || i64(iat) || i64(exp)
                       || lp(cert.pub) || lp(body)
```

`body` — непрозрачная строка, подписывается ровно в том виде, в каком лежит.
Разбирать её как JSON библиотека не обязана: это снимает требование к
одинаковой сериализации в Go и Dart.

`seq` — счётчик, растёт с каждой публикацией. Проверяющий запоминает
наибольший увиденный и не принимает меньший. Это защита от подсовывания
старого, но правильно подписанного конфига.

### 4.3. Отзыв (`revoke`)

```json
{ "v": 1, "min_epoch": 4, "iat": 1762400000, "by": "backup", "sig": "<подпись>" }
```

Подписываемая строка:

```
"awg-rotator/revoke/v1\0" || u32(min_epoch) || i64(iat) || lp(by)
```

Проверяющий запоминает `min_epoch` и перестаёт принимать сертификаты с меньшим
номером поколения. Пересобирать приложения для отзыва не нужно.

### 4.4. Команда (`command`)

От супер-клиента серверу. Подписана главным или запасным ключом напрямую,
сертификат здесь не участвует.

```json
{ "v": 1, "id": "<16 случайных байт>", "iat": 1762400000,
  "action": "move_region", "arg": "waw", "by": "root", "sig": "<подпись>" }
```

Подписываемая строка:

```
"awg-rotator/command/v1\0" || lp(id) || i64(iat) || lp(action) || lp(arg) || lp(by)
```

Действия: `move`, `move_region` (`arg` — регион), `status`, `revoke`
(`arg` — минимальное поколение).

Защита от повтора двойная: `iat` должен попадать в окно ±5 минут от текущего
времени, и сервер помнит уже исполненные `id`.

### 4.5. Регистрация устройства (`enroll`)

Каждое устройство имеет свой ключ туннеля и свой адрес. Регистрирует их не
человек: приложение само предъявляет ключ содержимого, называет себя, и сервер
добавляет его в список. Принадлежность приложению и есть право на регистрацию.

Оба сообщения — обычные конверты (раздел 2) с JSON внутри, без подписи: доказать
нужно только знание ключа содержимого, а его знает каждая сборка.

Запрос устройства:

```json
{ "v": 1, "kind": "enroll", "id": "<16 байт>", "pub": "<32 байта>",
  "nonce": "<16 случайных байт>", "iat": 1762400000, "name": "windows" }
```

- `id` — устойчивый идентификатор устройства. Приложение берёт хеш от того, что
  уникально для этой установки системы (на Windows `MachineGuid`, на Android
  `ANDROID_ID`), вместе с солью приложения. Повторная регистрация с тем же `id`
  заменяет ключ и сохраняет адрес, поэтому переустановка не плодит записей.
- `pub` — открытый ключ туннеля самого устройства (Curve25519, как в WireGuard,
  в base64url без выравнивания). Закрытая половина с устройства не уходит.
- `name` — подпись для человека, до 32 символов. Ни от чего не зависит.

Ответ сервера:

```json
{ "v": 1, "kind": "enrolled", "nonce": "<тот же>", "iat": 1762400000,
  "address": "10.8.0.7/32" }
```

Вместо `address` может быть `"error"`: `bad_request`, `busy` (слишком много
запросов, повторить позже), `full` (устройств уже столько, сколько сервер
держит), `key_in_use` (этот ключ закреплён за другим устройством), `pending`
(сервер пускает только одобренные устройства; заявка записана и ждёт решения
владельца, спросить ещё раз позже), `denied` (владелец отказал или отозвал
доступ). `nonce` повторяет запрос, чтобы чужой или запоздавший ответ не приняли
за свой.

**Одобрение.** Сервер может требовать одобрения владельца. Тогда новое
устройство, а также известное, но пришедшее с другим ключом, получает `pending`
и в туннель не добавляется, пока владелец не одобрит заявку. Одобренное
устройство с прежним ключом получает адрес сразу, как раньше. Чтобы владелец и
человек с устройством могли сверить, что речь об одном и том же, обе стороны
показывают код из четырёх цифр: первые 4 байта SHA-256 от строки
`awg-rotator/approval-code/v1`, за которой сразу идут 32 байта открытого ключа
устройства, как беззнаковое число big-endian по модулю 10000, дополненное
нулями слева. Код не секрет и ничего не доказывает, он только отличает одну
заявку от другой. Вектор — `approval_code` в разделе `enroll` файла
`vectors.json`.

**Как это ходит.** Сервер не знает ключа нового устройства, поэтому тот не может
подключиться напрямую. В конфиге есть служебный ключ поколения серверов (`enroll`
в теле конфига). С ним приложение поднимает туннель, у которого есть только один
адрес назначения — сам сервер, и отправляет запрос одной UDP-датаграммой на
`10.8.0.1:7843`. Датаграмма — строка конверта в UTF-8, ответ приходит так же. Из
служебного туннеля сервер ничего никуда не пересылает. После ответа приложение
снимает служебный туннель и подключается своим ключом и выданным адресом.

**Сервер проверяет:** запрос пришёл от служебного адреса; конверт открывается
ключом содержимого; `kind`, `v`, длины полей; `iat` в окне ±5 минут; частоту
запросов. Он помнит устройства в файле и передаёт их преемнику вместе с
остальным, поэтому известное устройство после переезда подключается сразу.
Забытая на сервере запись обнаруживается приложением само: рукопожатия своим
ключом нет, значит нужно зарегистрироваться ещё раз.

Контрольные векторы — раздел `enroll` в `vectors.json`: готовые конверты запроса,
ответа и отказа с фиксированным nonce. Порт обязан открыть их и получить
перечисленные там поля; свои конверты он запечатывает со случайным nonce.

### 4.6. Анонс версии (`release`)

Говорит приложениям, что вышла новая версия и где лежат установщики. Подписан
главным или запасным ключом напрямую, как команда: объявлять обновления может
тот, кто может командовать серверами.

```json
{ "v": 1, "version": "1.2.0", "build": 12, "min_build": 3,
  "iat": 1762400000, "notes": "что нового",
  "assets": [
    { "os": "windows", "url": "https://…/Rebirth-Setup-1.2.0.exe",
      "sha256": "<64 шестнадцатеричные цифры>", "size": 28311552 },
    { "os": "android", "url": "https://…/Rebirth-1.2.0.apk",
      "sha256": "<…>", "size": 19004416 } ],
  "by": "root", "sig": "<подпись>" }
```

Подписываемая строка:

```
"awg-rotator/release/v1\0" || lp(version) || u32(build) || u32(min_build)
    || i64(iat) || lp(notes) || u32(число установщиков)
    || для каждого: lp(os) || lp(url) || lp(sha256) || u64(size)
    || lp(by)
```

- `version` — для людей, вида `1.2.3` (допускается суффикс `-beta.1`).
- `build` — для машин, растёт с каждым выпуском. Приложение сравнивает его со
  своим номером сборки и предлагает обновление, если `build` больше.
- `min_build` — самая старая сборка, которая ещё работает с серверами. Если
  приложение старше, обновление обязательное. Не может быть больше `build`.
- `assets` — от 1 до 4 установщиков, по одному на платформу (`windows`,
  `android`), адрес только `https`. `sha256` пишется строчными буквами, `size` —
  в байтах, не больше 2 ГиБ.
- `notes` — до 4000 байт в UTF-8.

**Адрес — это только место, откуда скачать.** Что файл именно тот, определяет
`sha256`, а он подписан. Поэтому сервер, с которого качают, может отдать что
угодно, и приложение всё равно откажется ставить файл, не совпавший с подписью
по размеру или хешу.

Защита от отката: проверяющий запоминает наибольший виденный `build`
(`last_build`) и отбрасывает анонс с меньшим, чтобы правильно подписанным старым
анонсом нельзя было подсунуть старый установщик. Тот же `build` принимается:
повторное чтение файла не атака.

Смысл анонса проверяется и при выпуске: утилита оператора не подпишет анонс с
неверной версией, адресом не по https, хешем не той длины и тому подобным.

## 5. Порядок проверки документа

1. Расшифровать конверт ключом содержимого.
2. Разобрать JSON.
3. Проверить подпись сертификата ключом, названным в `cert.by`.
4. Убедиться, что `cert.epoch` не меньше запомненного `min_epoch`.
5. Убедиться, что текущее время попадает в окно `cert.nbf`…`cert.exp`.
6. Проверить подпись документа ключом `cert.pub`.
7. Убедиться, что `kind` совпадает с ожидаемым.
8. Для `config`: убедиться, что `seq` больше запомненного.
9. Убедиться, что документ не просрочен по `exp`.

На часы даётся допуск 5 минут в обе стороны.

Если хоть один шаг не прошёл, документ отбрасывается целиком, а запомненное
состояние не меняется.

## 6. Файлы в gist

Gist секретный, в нём несколько файлов, чтобы запись команды не задевала конфиг:

| Файл | Кто пишет | Что внутри |
|---|---|---|
| `c` | сервер | текущий конфиг (в нём служебный ключ для регистрации) |
| `s` | сервер | статус сервера |
| `q` | супер-клиент | команда серверу |
| `r` | супер-клиент | отзыв |
| `u` | супер-клиент | анонс версии (`release`) |

### Второе место

Те же пять файлов лежат ещё и в пакете `sync` (версия `1`) общего реестра пакетов
проекта на GitLab, под теми же именами. Это не копия, а равное место: ни одно из двух
не главное.

- **Запись.** Сервер и утилита оператора пишут в оба места. Запись удалась, если её
  приняло хотя бы одно; в какое не получилось, то отстало.
- **Догонка.** Отстающее место получает самую свежую проверенную версию каждого файла
  из другого, с тем же номером: новая версия при этом не выпускается. Версию, которая
  не новее лежащей, туда не пишут, поэтому заменённый сервер не затирает конфиг
  преемника.
- **Что значит «свежее»** определяется содержимым, а не местом, где файл найден, и
  только среди файлов, которые проходят проверку (подпись, срок): `c` и `s` — по `seq`,
  `r` — по `min_epoch`, `u` — по `build`, `q` — по времени выпуска. Побеждает больший
  номер, при равных — более позднее время выпуска.
- **Чтение.** Приложение читает оба места и принимает всё, что проходит проверку; номер
  и срок защищают от отката, поэтому порядок чтения не важен. Отзыв `r` применяется
  раньше любых конфигов: он может сделать негодным конфиг из другого места.
- **Права.** Читать пакет может кто угодно, это публичный проект. Писать серверам
  разрешает токен развёртывания проекта, который не даёт ничего, кроме чтения и записи
  его реестра пакетов.

## 7. Выбранные алгоритмы

- Подпись: Ed25519. Есть в стандартной библиотеке Go и в пакете `cryptography`
  для Dart.
- Шифрование: AES-256-GCM, случайный nonce на 12 байт. Тоже есть везде без
  лишних зависимостей. Публикаций за год порядка сотни, так что до опасного
  числа повторов nonce бесконечно далеко.
- Двоичное в тексте: base64url без выравнивания.
